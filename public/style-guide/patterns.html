Patterns

How the pieces compose.

Components answer "what does this look like"; patterns answer "how do they go together on a page." These are the reusable page-level shapes — pick the one that fits, then it's just content.

Honest current state

The shipped app carries three coexisting styling idioms: (1) Tailwind token classes (Overview, Rounds, ui.jsx) — the target; (2) inline style={'{ T.* }'} from theme.js (most of Chores.jsx) — the legacy idiom ui.jsx was built to retire; (3) inline color-mix() flush treatments (the new Schedule banners). New work uses idiom 1; idiom 2 gets folded in and deleted as files are touched.

Interactive affordance (the hover/active standard)

Interactive elements must look interactive — never lean on instructional text ("tap a block to see it" was the anti-pattern). One standard, the same on desktop and phone:

StateTreatmentToken
Rest, tappable in a dense strip A faint neutral "key" fill so the element reads as a control before any interaction — the rest-state signal where hover doesn't exist (touch). Use only when the element has no visual body of its own: the day-strip columns dropped it (42.3 round 3 — behind real bars it read as a backdrop, not an affordance) bg-row-active-dim
Hover A background tint that follows the cursor — a fill change, never a text-color-only change, and lighter rather than darker hover:bg-row-hover
Active / selected Filled background; a border bounding box only when the element is a row in a series (spine, This Week list) bg-row-active
Pressed (touch) The active fill while the finger is down — tap feedback on phones active:bg-row-active
Hover detail present A dotted underline beneath the identity badge — the abbr convention ("details on hover"), no instructional text. cursor: help normally rides along but yields when the element is also a click target (the pointer wins). border-b border-dotted border-faint

Carriers today: spine rows, the Day/Week/Month/Review tabs, This Week rows, ghost buttons (BTN_GHOST), and the mobile day-strip time columns (hover/press tints only). Hover detail beyond a short label uses the Tooltip primitive, never the native title attribute.

Mobile toolbar (primary + Add menu)

The phone shape for a page's action row (42.3 round 3, Schedule first): one primary action (Confirm, accent, flex-1) beside one consolidated "＋ Add" menu holding the secondary adds (Add chore · Add task · Add project step · Add buffer · Time off — round 4 folded the two context-anchored adds in and removed their in-card buttons) — never a wrapping row of text buttons. A context-anchored entry resolves its default target itself (the OPEN block when it fits, else the day's first eligible gap/block) and hides when the day offers no anchor. Both the primary action and the menu button are one row, equal height (same px-3 py-1.5 text-[12px] box); the Confirmed state occupies the same box and is a live control — tap to revert the day to a draft (Tooltip-cued). Menu/button hover+press go straight to bg-row-active (row-hover's 9% tint is imperceptible on the white menu surface). Status signals are not actions: the conflicts count disappears at zero on the phone and shows as a warn chip only when real. Desktop keeps the full toolbar row (it mirrors the two new entries as "Add step" / "Add buffer" text buttons). The menu is a flush anchored panel (border + shadow-md, sharp corners) over a transparent close backdrop.

Kind-tinted list rows

The list-group language for kinded rows (the day-spine): every row wears a light wash of its identity color — chore teal, project slate, event periwinkle — from the shared kindTint(cssVar, strength=11) util (ui.jsx), beside a solid, saturated 5px rail in the same color (uniform across kinds — no data encoded in the rail). The wash is an alpha background-IMAGE, never a background-color, so the row shell's hover/active/now tints show through; the kind badge (C/P/E) keys the color and wears the dotted hover-detail underline (see the affordance standard).

Planned vs unplanned time

One fill language for project time everywhere it's drawn (F9/F26): a gap with a real step in it is solid project slate; a free/unbooked gap wears the 45° blue cross-hatch — the wash-eggs ribbon pattern in --c-project, from the shared hatchUnplanned(strength) util (ui.jsx). Bare bars take full strength; row backgrounds with text on top take a light wash, and both fills are alpha images so hover/active row tints show through the gaps. Round 5: the sibling hatchCover(strength) speaks the same stripe language in --c-warn — a PLANNED block needing cover layers it over its flat kind tint (hatchCover(12)) until cover is accepted. Round 6: when the surface underneath is itself striped or a solid bar, needs-cover is the alternating hatchConflict(kindVar) — warn/kind diagonals, deliberately uneven (3px warn tick / 7px kind: a 50/50 alternation of two saturated hues strobes at bar size; thin ticks over the dominant identity color read as "warning ON the bar", not a third color). Never stack two hatch sets. Carriers: free+needs-cover spine project rows (light 14/10), day-load conflict bars (full — the fill IS the stripes, no warn border), the phone strip's chore remainder + project columns.

Approval queue (Proposals)

Where actions an external Claude chat proposes land for human sign-off. Pending / History tabs over a stack of flush ProposalCards; Approve runs the app's real create path, Reject discards. Nothing an agent proposes mutates data until it's approved here — surface + prompt, never silent mutation. Backed by agent_proposals + useAgentProposals; proposals arrive live via realtime, so one queued from a phone shows up instantly. The agent's write tools are propose-only, which keeps a future public (phone / claude.ai) endpoint low-risk — it can only enqueue, never corrupt.

Live HTML doc (attachments)

An attached .html file opens as a working page, not a download. LiveDocViewer renders it full-screen in a sandboxed iframe (allow-scripts allow-forms — opaque origin, so the page can't reach the app session or real storage) and injects a shim that swaps the page's localStorage for a per-attachment key/value store (attachment_doc_data). Per-KEY rows mean two people editing different keys never clobber each other; edits sync via realtime into an open page as storage events.

The doc opens read-only; Edit claims the advisory write lock (attachment_doc_locks, 30s heartbeat, 90s stale cutoff — a closed laptop never wedges the doc), Done releases. The other editor sees a live lock chip.

Project URLs & attachment deep links

Projects live at /projects/<slug> — an immutable slug derived from the title once (lib/slug.js); retitling never rewrites it, and old uuid links still resolve (the page canonicalizes them to the slug). Every attachment row carries a ghost Link2 copy-URL action (flips to an accent check for 1.5s); its link, /projects/<slug>/files/<id>, reopens that file — the LiveDocViewer for live HTML docs, a signed URL in a new tab for everything else. Phase headers wear the same hover GripVertical drag-reorder grip as steps and ranked projects, and the "Linked to" section links projects to other projects alongside events and chores.

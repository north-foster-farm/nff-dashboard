Field-ops design system · living reference

A bounded set of ways things look.

This is the source of truth for how the NFF farm dashboard looks and how its pieces fit together. The design language is settled here — color, type, shape, the components and when to use them — so that building a screen is mostly a question of layout and structure, not of inventing a look each time. If a treatment isn't in this system, it isn't an option yet.

How to use it
Browse it like any framework's docs — every swatch and example is rendered from the real tokens, so the theme toggle (top right) re-skins the whole site, proving the token layer. When Claude builds, it reads the same system from DESIGN-SYSTEM.md (the machine reference) and the canonical source files this doc cites.

Maturity tags

We iterate aggressively, so a treatment's status is part of its documentation. Every component and pattern carries one:

Stable shipped and ratified — build on it freely.    Converging the agreed direction, partly shipped — build toward it; expect the old form still in places.    Proposed decided in design, not yet built — don't rely on it in code.

Principles

Nine rules that decide the close calls. They are ranked: when two conflict, the earlier one wins.

1 · Flush, not raised

Panes are defined by a hairline border on the page background, not by a raised surface in a different color. Figure-ground comes from the line, not from stacking another fill. The one exception is a floating element over a scrim — sheets, modals, trays keep a raised surface, because a figure over a dimmed page needs it.

2 · Color is functional, never decorative

A hue always means something: green is resolved, amber is caution, the category colors map to real event kinds, the project hue is calm time. We never reach for color to liven a screen up. A surface with no state to signal stays in the neutral text/border tokens.

3 · Sharp corners

Cards, panes, rows, and inputs are square. Only genuinely circular things round — status dots, avatars, toggle knobs, count badges. Rounding a card reads as a different product; don't.

4 · Three type roles, no fourth

Lora (serif) carries headings and the few hero numbers. Inter sets every uppercase eyebrow and label. Nacelle is the body voice for everything else. Each role has a job; a screen never mixes a fourth family or uses a face outside its role.

5 · Tokens only — the theme decides the value

Never a raw hex in a component. Color, through the --c-* tokens, follows the active theme automatically; both light and dark must read. If you need a value the tokens don't have, that's a system change, not a one-off.

6 · Field reality decides the tie

The phone is the deciding tier: one-handed, gloves on, sun on the screen, signal dropping. A treatment that's only legible on a calm desktop loses to one a covered operator can parse cold. Must-see states — needs-cover, overdue, offline — stay loud everywhere.

7 · A bounded list of options

For any given job there is one canonical component or treatment, with a named, finite set of variants. The value of this system is the closing of the option space — fewer decisions, more consistency. New looks are proposed here first, not improvised in a page.

8 · Fold the old in, then delete it

This is a two-person tool with high tolerance for change: each iteration replaces the prior form and removes it, rather than leaving a dual-source shim to soak. The same applies to display — never mutate committed data as a side effect of showing it; surface the change and let the operator act.

9 · Words are design material

Copy is part of the look. Plain verbs, active voice, sentence case. Name things by what the operator controls, not by how the system is built. An action keeps its name through the whole flow; an empty state invites an action; an error says what happened and how to fix it.
